Candidate Assignment | Followed by a Technical Discussion 
Build a small, enterprise-style workforce management application that lets an organization manage its employees, 
departments, positions, reporting hierarchy, leave requests and bulk employee imports. The application must support three 
user roles, and every permission must be enforced on the backend. 
Before you start: please read the full document. The scope is intentionally broad, and Section 2 explains what to build 
first. We do not expect a production-ready HR platform. A smaller set of features that work end to end and are well 
reasoned is valued more than a large set that is half finished. 
1. Objective 
Design and build a working full-stack application. The assignment is meant to show us how you: 
• design a relational data model with the right keys, constraints and indexes; 
• implement business rules on the backend and expose them through clean, consistent APIs; 
• handle concurrency correctly, both for background processing and for simultaneous updates; 
• secure APIs with authentication and role-based access control; 
• build a usable, role-aware frontend; and 
• test your work and explain your design decisions and trade-offs. 
Technology choice: you are free to use any frontend framework, backend language and framework, and relational 
database that you are comfortable with. Choose tools that let you deliver a working solution, and briefly explain your 
choices in your solution document. Do not integrate with SAP HCM, SuccessFactors or any other external enterprise 
system; use generated sample data and seeded users for the three roles.

3. User Roles and Permissions 
The application must support the following three roles. The responsibilities below define who initiates each operation. Do 
not assume that every user can perform every action. 
HR Administrator: Responsible for organization-wide administration: employee records, bulk imports, departments, 
positions, employee-position assignments, reporting relationships and approval-workflow configuration. Can view 
organization-wide employee and leave information. 
Manager: Responsible for their team: viewing direct and indirect reports, reviewing leave requests from direct reports, and 
approving or rejecting requests when the workflow assigns them an approval step. 
Employee: Responsible for self-service activities: viewing their own profile, updating permitted personal details, applying 
for leave, and tracking their own leave balance and request history. 
Every user account is linked to an employee record. Managers and HR Administrators are also employees, so they can use 
all Employee self-service features for their own record (for example, applying for their own leave). A Manager’s team is 
defined by the reporting hierarchy: their direct and indirect reports. 
Seed at least one HR Administrator, two Managers (one reporting to the other) and several Employees, so that direct and 
indirect reporting can be demonstrated.

4. Functional Requirements 
4.1 Employee Management 
Who performs these tasks: HR Administrator creates, edits and deactivates employee records. Employees can view their 
own profile and update only permitted personal fields. Managers can view the profiles of their direct and indirect reports but 
cannot edit employee master records. 
• HR Administrator can create an employee with employee ID, name, email, date of joining, department, position, 
manager and employment status. Employee ID and email must be unique. 
• HR Administrator can update employee details, change department, position or manager, and deactivate an employee. 
Deactivation is a soft delete: the employee’s history (leave, assignments and approvals) must be preserved, and a 
deactivated employee cannot log in. 
• Decide how you handle a deactivated employee’s direct reports, active position and pending approval tasks, and 
document your choice. 
• Employees can view their own profile and update only self-service fields (for example, phone number or address). The 
backend must reject attempts to change any other field. 
• Managers can view the profiles of their direct and indirect reports. Define which fields are restricted (for example, home 
address), make sure the API does not return them to Managers, and document the list. 
• Provide an employee listing with server-side search, filtering (at least by department and employment status), sorting 
and pagination. HR Administrator can search organization-wide, a Manager can search only within their team, and an 
Employee can access only their own record. 
4.2 Bulk Employee Import 
Who performs these tasks: Only the HR Administrator can upload and initiate a bulk employee import. Managers and 
Employees must not be allowed to upload employee master data. 
• HR Administrator uploads a CSV or Excel file of employee records. Unsupported file types and oversized files are 
rejected with a clear message. 
• Each row is validated for required fields, email and date formats, department, position and manager references, and 
duplicate employee IDs or email addresses (both within the file and against existing records). 
• Valid rows are imported; invalid rows are rejected with the row number and a clear error reason. One invalid row must 
not cause valid rows to fail. 
• Show an import summary with total rows, successful rows, failed rows and the job status (for example: Queued, 
Processing, Completed, Completed with errors, Failed). 
• HR Administrator can download a failed-row report (original row data plus the error reason), correct the rows and 
upload them again. Re-uploading rows that were already imported must not create duplicates; decide whether such 
rows are skipped or reported, and document it. 
• The import runs asynchronously using a bounded thread pool or an equivalent controlled background-processing 
mechanism. The UI shows job status and progress (polling is fine). See Section 5.1.

4.3 Department and Organization Management 
Who performs these tasks: Only the HR Administrator creates, edits or deactivates departments and defines parent-child 
department relationships. Managers and Employees may view the relevant organization structure but cannot change it. 
• Support departments and sub-departments through parent-child relationships. Each department has a unique 
department code. 
• HR Administrator can create, update and deactivate departments. A department cannot be made a child of itself or of 
one of its own sub-departments. 
• A department that still has active employees or active sub-departments cannot be deactivated; return a clear error. 
• Display the organization hierarchy as a tree or an equivalent visual representation. 
• Managers can view their own reporting hierarchy and team structure. Employees can view the department hierarchy 
and their own reporting line (their chain of managers) in read-only mode. 
4.4 Position Management and Employee Assignment 
Who performs these tasks: Only the HR Administrator creates and manages positions and assigns employees to 
positions. Managers and Employees have read-only access to the position information they are permitted to see. 
• HR Administrator can create and update positions with a unique position code, title, department and, where 
applicable, a reporting position. 
• HR Administrator can assign an employee to a position with an effective start date, and end an assignment with an end 
date. 
• Keep the full employee-position assignment history; never overwrite past assignments. 
• A position can have at most one active employee assignment at a time, and an employee holds at most one active 
position at a time. Assigning an employee to a new position ends their previous active assignment in the same 
transaction. 
• Vacant positions must be easy to identify (for example, through a filter on the position list). 
• If two HR Administrators try to assign different employees to the same vacant position at the same time, at most one 
assignment may succeed. The other request must receive a clear conflict response (HTTP 409). See Section 5.2. 
4.5 Reporting Relationships and Hierarchy Validation 
Who performs these tasks: The HR Administrator sets or changes an employee’s manager. Managers and Employees can 
view the reporting hierarchy permitted for their role but cannot edit reporting relationships.

• Support direct and indirect reporting relationships. Only active employees can be assigned as managers. 
• Provide APIs to retrieve a manager’s direct reports and their full reporting tree (all descendants). 
• Prevent circular reporting relationships, including self-reporting (A reports to A), direct cycles (A reports to B and B 
reports to A) and indirect cycles (A → B → C → A). 
• Explain the approach used to detect cycles and retrieve descendants. See Section 5.4. 
4.6 Leave Management and Approval Workflow 
Who performs these tasks: All users (Employees, Managers and HR Administrators) can submit leave requests for 
themselves. Managers approve or reject requests when assigned as an approver. HR Administrator configures the approval 
workflow and performs HR-level approval when that step is part of the configured workflow. 
• An employee can submit a leave request with leave type, start date, end date and reason. 
• Seed at least three leave types (for example, Casual, Sick and Earned) with a fixed annual balance for each employee. 
Accrual, carry-forward and payroll or external HR integration are not required. 
• Count leave in working days (Monday to Friday). Public holidays and half-day leave can be ignored. 
• Validate required fields, date ranges, overlaps with the employee’s own pending or approved requests, and available 
balance. Pending requests count against the available balance, so several pending requests together cannot exceed it. 
The balance is consumed when the request is finally approved and released if it is rejected. 
• Each request follows a configurable, sequential approval workflow stored in the database, for example Manager 
approval followed by HR approval. Each step defines who may act on it (for example, the requester’s manager, or any 
HR Administrator). 
• The manager step is assigned to the requester’s direct manager, so a Manager’s own leave goes to their own manager. 
Decide and document what happens when a requester has no manager. 
• Approving a step moves the request to the next step; approving the final step marks it Approved. Rejecting at any step 
ends the workflow and marks it Rejected. A comment is mandatory when rejecting. 
• No one may act on their own leave request, and only an authorized approver can act on the current step. 
• HR Administrator can configure the approval steps. Changing the configuration must not break requests that are 
already in progress; document how you handle this. 
• Employees can view only their own requests, balances and approval history. Managers can view requests assigned to 
them and the leave status of their team. HR Administrator can view all requests. 
• Maintain an approval history with approver, action, comment and timestamp. Prevent duplicate actions and invalid 
status transitions, including two approvers acting on the same step at the same moment. 
5. Key Technical Challenges (Mandatory) 
These four areas carry the most weight in the evaluation. Be prepared to explain each of them in detail during the 
discussion. 
5.1 Concurrent Bulk Import Processing 
Process imports with a bounded thread pool, worker pool or job queue with a fixed concurrency limit. Do not create an 
unbounded number of threads or workers, and do not load a large file entirely into memory when it can be streamed or read 
in batches. Track job progress and isolate row-level failures so that one bad row or batch does not stop the job. 
Demonstrate the implementation with a sample file of at least 1,000 rows containing valid, invalid and duplicate records, 
and include that file (or a script that generates it) in the repository. Explain how you chose the pool size and batch size. 
5.2 Concurrent Position Assignment 
Enforce the one-active-employee-per-position rule so that it holds even under simultaneous requests. Use an appropriate 
strategy, such as a database constraint, optimistic locking or pessimistic locking, and explain why you chose it. A simple 
“check if vacant, then insert” in application code is not sufficient on its own. Prove the behavior with an automated test that 
sends simultaneous assignment requests and asserts that exactly one succeeds and no position ends up with two active 
assignments.

5.3 Configurable Approval Workflow 
Approval steps must be data-driven rather than hard-coded to a single fixed sequence: adding, removing or reordering a 
step should need a configuration change, not a code change. Validate who is allowed to act at each step, prevent duplicate 
or conflicting actions, and keep a complete audit history. 
5.4 Hierarchy Cycle Detection 
Prevent any reporting change that would create a cycle. Document the algorithm or database approach you used and 
include tests for self, direct and indirect cycles. 
6. Suggested Data Model 
You are expected to design the database schema. The following are suggested entities, not a prescribed schema: 
• Users and Roles 
• Employees 
• Departments 
• Positions 
• Employee Position History 
• Leave Types and Leave Balances 
• Leave Requests 
• Approval Workflows, Approval Steps and Approval History 
• Import Jobs and Import Errors 
Use appropriate primary and foreign keys, unique constraints, indexes and transactions, and manage the schema through 
database migrations. Explain important design decisions in your solution document. 
7. Frontend Requirements 
Build role-aware screens for the following: 
• HR Administrator: employee management, bulk import, department and position management, organization 
hierarchy, workflow configuration and organization-wide leave overview. 
• Manager: team directory and hierarchy, leave requests awaiting their approval, and team leave status. 
• Employee: own profile, permitted profile updates, leave application, leave balance and request history. 
• Bulk import: file upload, validation and processing status, success and failure counts, and failed-row download. 
Show appropriate loading, empty, validation, error and unauthorized states. Hiding a control in the UI does not replace 
backend authorization. 
Visual polish is not the focus. A clean, consistent and usable interface is enough, and you may use any UI component 
library. 
8. Non-Functional Requirements 
• Enforce role-based access control on every protected backend API, including data-level checks. For example, a 
Manager must not be able to fetch an employee outside their team by changing an ID in the request. 
• Validate input on both frontend and backend; backend validation is authoritative. 
• Return clear, consistently structured error responses with appropriate HTTP status codes, using centralized exception 
handling. 
• Use transactions for operations that must succeed or fail together. 
• Keep the code modular, readable and maintainable.
